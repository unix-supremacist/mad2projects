# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A native mod loader + set of compatibility/QoL/chaos mods for **Madagascar 2: The Game** (`Mad2.exe`, a 32-bit Windows game), targeting Linux via Proton/Wine (`umu-run` + `gamescope`). The core is C++17 compiled to 32-bit Windows DLLs via MinGW cross-compilation, loaded into the game process — there is no Linux-native binary for these. `mad2/` is the actual game install directory (mostly game assets/DLLs, gitignored-style content); `mad2russia/` and `mad2demo/` are additional installs (Russian localization, demo) sharing the same wineprefix and mod set. The Windows-DLL mod source lives in ~21 top-level project directories, each an independent CMake target producing one DLL — see Architecture below for the full list and how they relate.

Beyond the in-process DLLs, a few pieces run outside the Wine process entirely, orchestrated by `justfile` alongside the game:
- **`mad2relauncher/`** and **`mad2launcher/`** — Go programs (native Linux binaries, plain `go build`, no MinGW).
- **`mad2music/`** — a native Linux C++/SDL3 executable with its own separate CMake project (not part of the root MinGW cross-build). Also cross-builds for native Windows (`just build-music-windows`, i686-w64-mingw32 + a fetched SDL3-devel-mingw release) for native-Windows Mad2 installs, where there's no `mad2relauncher` to supervise it — see `mad2podcastmod`'s native-Windows startup branch below.
- **`extern/sm64ex-alo/`** — a vendored third-party SM64 PC port, built both native-Linux and cross-compiled for Windows via its own Makefile (not CMake).
- **`extern/jak-project/`** — a vendored fork of the OpenGOAL `jak-project` decompilation/runtime (fetched from `github.com/open-goal/jak-project`), the engine behind `mad2companionmod`'s chaos effect `JakChallenge`. Built via its own `task`-based build system (not CMake), native-Linux only (`just build-jak1-linux`, needs a user-supplied `jak1.iso`); produces `build/game/gk` (the runtime) and `build/goalc/goalc` (the GOAL compiler/REPL, used to rebuild `goal_src/` after touching any GOAL-side patch). See `mad2companionmod/src/jak1mod.cpp` and `mad2relauncher/jak1.go` for the two ends of the integration.
- **`extern/mario-legacy/`** — a vendored *separate* jak-project fork, `OpenGOAL-Mods/Super-Mario-Legacy` (release v0.0.28, prebuilt Linux **and Windows** binaries — `gk`/`goalc`/`extractor` and `gk.exe`/`goalc.exe`/`extractor.exe` side by side, sharing one `data/` tree confirmed byte-identical between the two platform archives — `libsm64` statically linked into `gk`), the engine behind `mad2companionmod`'s third chaos effect, `MarioLegacyChallenge`. Not layered onto `extern/jak-project` — a wholly independent checkout/build with its own `goal_src` (restructured under a `data/` subdirectory, unlike `extern/jak-project`'s own top-level layout) and its own `engine/mods/mario/` gameplay code swapping Mario in for Jak. No C++ build step (`just setup-mario-legacy` only extracts assets from the same `jak1.iso` `extern/jak-project` uses, symlinked in, plus a symlinked Super Mario 64 `.z64` ROM reused from `extern/sm64ex-alo/baserom.us.z64` for `libsm64`, and recompiles `goal_src/` with the fork's own vendored `goalc`). Carries the same controller-injection patch as `extern/jak-project`'s `pad.gc` (confirmed byte-identical otherwise), ported separately since the two forks share nothing at the source level. Unlike `JakChallenge`, `MarioLegacyChallenge` has a real native-Windows `CreateProcess` branch (see `mad2companionmod/src/mariolegacymod.cpp`) since a Windows build already exists upstream — `JakChallenge`'s own upstream (`open-goal/jak-project`) has no equivalent (MSVC/Windows-clang only, no MinGW path, a materially bigger lift; not attempted). See `mad2companionmod/src/mariolegacymod.cpp` and `mad2relauncher/mariolegacy.go` for the Wine-side integration.
- **`mad2rando5/`** — the level-logic randomizer that drives `mad2levelredirectmod` via `level_redirects.txt`, migrated in-repo from a formerly-external sibling. Standalone Go module, no dependencies beyond stdlib. `mad2launcher`'s "Mad2 Randomizer" category builds/runs it automatically; `just build-mad2rando5` builds it directly.
- **`mad2iga/`**, **`mad2arc/`**, **`mad2repack/`**, **`mad2tool/`**, **`mad2save/`**, **`mad2savegui/`**, **`mad2transitions/`** — the IGA archive/save-editing toolset, migrated in-repo from a formerly-external `mad2assetextractor` sibling and split one Go module per tool (matching this repo's own per-project convention instead of that repo's single-module `cmd/`+`pkg/` layout). `mad2iga` is the shared archive-format library the other tools that need it (`mad2arc`, `mad2repack`, `mad2tool`) import via a local `replace` directive in their `go.mod`; `mad2save`/`mad2savegui`/`mad2transitions` are fully standalone. `mad2launcher`'s save editor (the "Cheats" category) is a from-scratch reimplementation of `mad2savegui`'s cheat-toggle logic, not a caller of it — the two are independent. `just build-assettools` builds all six at once. Beyond the IGA archive container, `mad2iga` also now implements a real Section-1 IGZ object-graph walker (`objgraph.go`), a PC/Wii-cross-verified per-class field schema (`schema.go`), and FSB3 audio + `.texs` texture parsing (`fsb.go`/`texture.go`) — see `docs/` (below) for the full reverse-engineering writeup; this is a large, ongoing effort distinct from the mod-loader DLLs above.

This repo also references `../mad2mod`, an external sibling repo this repo's chaos-effects/audio/save-editing logic is progressively ported from (an older Go+SDL external overlay tool, process-external, read/wrote `Mad2.exe`'s memory via `process_vm_readv`/`writev`). It does not live inside this working directory and has not been migrated in.

## Build commands

Uses `just` (see `justfile`) as the primary interface, backed by CMake + Ninja (via `samu`) with a MinGW i686 cross-toolchain:

```sh
just configure          # cmake -S . -B build -G Ninja -DCMAKE_TOOLCHAIN_FILE=cmake/mingw-i686.toolchain.cmake ...
just build               # configures if needed, then cmake --build build
just deploy-mad2          # build, then copy version.dll + mods/*.dll into mad2/
just deploy-mad2russia    # same, into mad2russia/
just deploy-mad2demo      # same, into mad2demo/
just build-relauncher     # go build mad2relauncher/ -> build/mad2relauncher (native Linux)
just build-launcher       # go build mad2launcher/ -> build/mad2launcher (native Linux GUI)
just run-launcher          # build-launcher, then run it (expects cwd with mad2/, mad2russia/, mad2demo/ one level down)
just build-mad2rando5      # go build mad2rando5/ -> build/mad2rando5 (level-logic randomizer CLI)
just build-assettools      # go build mad2arc/, mad2repack/, mad2tool/, mad2save/, mad2savegui/, mad2transitions/ -> build/
just build-sm64-linux      # native-Linux build of extern/sm64ex-alo (needs a user-supplied baserom.us.z64); prefers the "mad2-debian" distrobox if present
just build-sm64-windows    # best-effort i686-w64-mingw32 cross-build of extern/sm64ex-alo, for mad2companionmod's real-Windows branch
just build-jak1-linux      # native-Linux build of extern/jak-project (needs a user-supplied jak1.iso); prefers the "mad2-debian" distrobox if present, mirrors build-sm64-linux's shape
just setup-mario-legacy    # extracts/compiles the prebuilt extern/mario-legacy fork (no C++ build step; needs jak1.iso + a Super Mario 64 .z64 ROM, both symlinked in from the other two forks' copies)
just build-music-linux     # native-Linux build of mad2music/ (own CMake project, needs sdl3 via pkg-config) -> build/mad2music
just build-music-windows  # best-effort i686-w64-mingw32 cross-build of mad2music/ (fetches SDL3-devel-mingw), for native-Windows Mad2 installs -> build/windows/{mad2music.exe,SDL3.dll}
just build-xdeltagen       # native-Linux build of mad2xdeltagen/ (own CMake project) -> build/mad2xdeltagen -- produces *.mad2xdelta patches for mad2xdeltamod.dll, see docs/IGA_FORMAT.md
just fetch-libretro-fceumm # fetches the libretro buildbot's 32-bit Windows FCEUmm core -> extern/.libretro-cores/fceumm_libretro.dll, for mad2nesmod's NesChallenge/NesLostLevelsChallenge effects (`run` depends on this; the ROMs themselves, roms/smb1.nes + roms/smb2j.fds + roms/disksys.rom, are still user-supplied -- see roms/README.md)
just fetch-libretro-mupen64plus # same shape, for mupen64plus_next_libretro.dll -> extern/.libretro-cores/, mad2nesmod's N64Sm64Challenge effect (`run` depends on this too; roms/sm64.z64 is still user-supplied -- see roms/README.md)
just run                  # deploy-mad2 + build-relauncher + build-music-linux, then launch Mad2.exe via mad2relauncher (wraps gamescope+umu-run)
just run-mad2russia       # same for mad2russia/
just run-mad2demo         # same for mad2demo/, launching Mad2Demo.exe
just regedit / shell      # open regedit / a shell inside the game's Proton prefix
just clean                # rm -rf build
```

None of `build-sm64-linux`, `build-jak1-linux`, or `setup-mario-legacy` is a dependency of `run`/`run-mad2russia`/`run-mad2demo` (all three need a user-supplied ROM/ISO not part of this repo) — `_play` soft-checks for each built binary and just warns + disables the corresponding chaos effect (`SM64Challenge`/`JakChallenge`/`MarioLegacyChallenge`) if it isn't built yet, rather than failing the whole launch. `mad2relauncher`'s `-music-path`/`-music-audio-dir` flags are how `mad2music` gets picked up at runtime once built.

There is no test suite — these are hook-based DLLs that only make sense running inside the actual game process. Validation is: build cleanly, deploy, launch the game, check the log files (see Logging conventions below). **Do not attempt to screenshot the running game window to verify a change** — it runs inside gamescope under Proton/Wine and is not something you have a reliable way to capture or view; rely on log output (per-mod `*.log` files) and ask the user to confirm anything visual in-game. All three game installs share a single wineprefix (`./wineprefixes/mad2`).

Toolchain requires `i686-w64-mingw32-gcc`/`g++`/`windres` on PATH, plus `samu` (a Ninja-compatible build tool) and optionally `ccache` (auto-detected in `CMakeLists.txt`). All targets link `-static -static-libgcc -static-libstdc++` so no libgcc/libstdc++ DLLs need to be shipped into the Wine prefix. Shared-API mods (anything another mod resolves by name via `GetProcAddress`, e.g. `mad2xinput`, `mad2config`, `mad2effects`) additionally link `-Wl,--kill-at` to strip MinGW's stdcall `@N` decoration from exported symbol names — without it every `GetProcAddress(h, "Mad2Xxx_Yyy")` lookup would fail since the export table would hold `Mad2Xxx_Yyy@N` instead.

Running the game directly (bypassing `just`): `./run_game.sh [play|regedit|shell|help]`. It sets `WINEPREFIX`, `PROTONPATH` (defaults to a `GE-Proton10-34` install, falls back to searching Steam's `compatibilitytools.d`), and critically `WINEDLLOVERRIDES=version=n,b` — this makes Wine prefer the native `version.dll` (the mod loader) over its builtin one, which is what makes the whole mod chain load in the first place. `play` runs the game inside `gamescope`.

## Architecture

### Load chain

`Mad2.exe` → `AWL.dll` imports `version.dll` → because of the Wine DLL override, this resolves to **our** `version.dll` (built from `modloader/`) instead of the system one. This is deliberate: it loads very early (before `Mad2.exe`'s own entry point runs) without contending for `d3d9.dll`/`xinput1_3.dll`/`dinput8.dll`, which other compatibility layers (DXVK, dxwrapper, ReShade) already want to own.

1. **`modloader/`** builds `version.dll` (`OUTPUT_NAME "version"`, static-linked). Its `DllMain`:
   - `InitVersionProxy()` (`version_proxy.cpp`) — loads the *real* system `version.dll` by full path from `GetSystemDirectoryA` (never by bare name, to avoid recursively loading itself) and resolves every export. The DLL re-exports all of `version.dll`'s API (`version.def`) as thin forwarding stubs, so anything that depends on the real `version.dll` keeps working transparently.
   - `LoadMods()` (`mod_loader.cpp`) — enumerates `<exe dir>/mods/*.dll`, **sorts the filenames (case-insensitive, alphabetical) before loading**, and `LoadLibraryA`s each one in that order. Each mod's own `DllMain` is its entry point for installing hooks. This sort is deliberate, not incidental: which mod's D3D9 hook ends up "outermost" (draws/captures first each frame — see "D3D9 overlay hooking" below) is entirely determined by load order, and `zz_mad2graphicseffectmod.dll`'s filename prefix specifically exploits this to guarantee it always loads (and thus hooks) last.
   - Logs via the shared cross-DLL logger (see "Logging conventions" below) to `<exe dir>/logs/mad2.log`, not a dedicated `mad2modloader.log`.

2. **Mods deployed into `mad2/mods/`** (each an independent DLL, loaded by step above). Grouped by role:
   - **File/IO redirection**: `mad2assetloader`, `mad2saveloader`, `mad2levelredirectmod` — see "The IAT hooking pattern" below.
   - **Shared APIs other mods resolve by name**: `mad2xinput`, `mad2config`, `mad2effects`, `mad2levelredirectmod`, `mad2hookutil`, `mad2textrenderer` — see "Shared-API mods" below.
   - **Diagnostics/fixes**: `mad2shadowfix` — see its own section below.
   - **Informational overlays**: `mad2igttimer`, `mad2playercoords`, `mad2inputdisplay`, `mad2twitchchat`, `mad2musichud` — see "Other overlay mods" below.
   - **Chaos-effects system**: `mad2inputeffectsmod`, `mad2graphicseffectmod`, `mad2chaosmod`, `mad2effectshud`, `mad2twitchcontrolsmod`, `mad2companionmod`, `mad2podcastmod`, `mad2gameeffectsmod`, `mad2nesmod` — see "The chaos-effects system" below.
   - **Persistent toggleable modes**: `mad2mirrormod` (deployed as `zz_mad2mirrormod.dll`, same load-order reasoning as `zz_mad2graphicseffectmod.dll`) and `mad2minigamemodefix` — see their own sections below. Neither is part of the chaos-effects system; both are full-session on/off behavior, not a randomized/timed effect.
   - **Not yet written up below**: `mad2cheatapply` (title-screen cheat-toggle mod — a configurable key/controller-combo writes the engine's built-in cheat-toggle struct directly via a hand-derived pointer chain off `AlchemyCommonLib.dll`, an in-process port of `../mad2mod`'s external `enable_all_cheats()`) and four dev-only diagnostics, none meant to stay loaded permanently, none part of general mod-loader architecture — all part of the `docs/` reverse-engineering effort: `mad2rhythmlogger` (vtable-patches `execute()` on VolcanoRave rhythm-minigame opcode classes in `ScriptInfoLib.dll` to log runtime arg-stack resolution while a song plays), `mad2climbprobe` (memory-dump probe originally built for the climb-ability/monkey-collectible investigation, F-key hotkeys to dump/toggle/scan process memory; also grew the live-object-naming scan (`M`/`U`/`J`/`K` hotkeys) that found `mad2minigamemodefix`'s target variable — see that mod's own section below for what those hotkeys found and why), `mad2metadumper` (reads the Alchemy engine's own live class registry — every registered class, parent chain, complete field list — straight out of the running game; this is the actual source of `mad2iga/live_reflection_schema.json`, see `docs/CLASS_SCHEMA.md`'s "Live reflection dump" section), and `mad2shoptrace` (same vtable-patch-`execute()` technique as `mad2rhythmlogger`, applied to `OpForEach`/`OpSpawn`/`OpChangeMembership`/`OpFindSubSet`/`OpCheckMembership`/`OpCreateVariable` and gated to the Duty Free level, built to chase why several shop items never appear in-game — see `docs/SCRIPT_FORMAT.md`'s Round 9). Also `mad2xdeltamod` (inline-hooks `igIGZLoader::parseSections` in `igCore.dll` to apply `xdelta_patches/*.mad2xdelta` binary diffs to a `.pak`'s already-decompressed bytes in memory — the distribution answer to "can't ship a whole edited `.bld`"; same-length string edits confirmed working live, growing edits still an open crash — full writeup, every reverse-engineered offset, and current status in `docs/IGA_FORMAT.md`'s own section). Its offline counterpart, `mad2xdeltagen` (native Linux CLI producing `.mad2xdelta` files from original/modified byte pairs), is not part of this MinGW cross-build — own CMake project, `just build-xdeltagen`, same pattern as `mad2music/`.

### Shared-API mods

`mad2xinput`, `mad2config`, and `mad2effects` are not consumed by anything outside this process — they exist purely so other mods don't each have to reimplement the same hook/registry. The pattern, used identically by all three:

- The mod exports plain `extern "C" __declspec(dllexport) ... WINAPI` functions from its DLL (`mad2xinput.dll`, `mad2config.dll`, `mad2effects.dll`), linked with `-Wl,--kill-at` (see Build commands above for why).
- Consumers do **not** link against it at build time (`mad2/mods/*.dll` load order isn't guaranteed — the dependency might not exist yet at any given mod's `DllMain`). Instead each shared-API mod ships a public header (`include/mad2xxx_api.h`) with function-pointer typedefs and an inline `Mad2Xxx_Resolve()` helper: `GetModuleHandleA(dllName)` + `GetProcAddress` per export, cached in a function-local `static`, resolved **lazily** (first per-frame hook call, or a background thread's first iteration for mods with no per-frame hook — never from `DllMain`) since the dependency is guaranteed loaded by then even if it loaded after the consumer.
- Callers null-check every resolved function pointer before use and log a one-time `"[Dependency] ... not found"` line if it's missing, rather than crashing.

What each one owns:
- **`mad2xinput`** (`mad2xinput_api.h`) — hooks `XInputGetState` at the IAT level (ordinal 2 in `xinput1_3.dll`, imported by `igDisplay.dll`; **not** by name — see `xinput_api.cpp`'s comment on why hardcoding the wrong ordinal here crashes instantly). Caches each controller's raw pre-override state (`Mad2XInput_GetState`, what `mad2inputdisplay` and hotkey-combo detection read) and exposes a **layered override** system: `Mad2XInput_AddOverride`/`UpdateOverride`/`RemoveOverride`, handle-based, where every mod's active override layer for a controller is applied in sequence (hold/block buttons → swap A/B, X/Y → invert axes → scale magnitude → block specific stick directions → force exact values, in that order) inside `HookXInputGetState`. This replaced an earlier single-slot `SetOverride`/`ClearOverride` API specifically because `mad2inputeffectsmod` needs several independent effects (e.g. joystick reversal + a button-swap + a phantom button-press pulse) active on the same controller simultaneously without clobbering each other.
- **`mad2config`** (`mad2config_api.h`) — owns `<exe dir>\config.cfg`, a hand-rolled `[Section]`/`Key=Value`/`# comment` format (no third-party parser, deliberately — see the file header in `config_dll.cpp`). Every `Get*` is "read or seed default": if the key doesn't exist yet, the default is written back immediately with the given comment rendered above it, so the file is self-documenting on first run. This is why `config.cfg` grows a new block of keys the first time each mod actually runs.
- **`mad2effects`** (`mad2effects_api.h`) — the chaos-effects registry; see "The chaos-effects system" below for the full contract.
- **`mad2levelredirectmod`** (`mad2levelredirect_api.h`) — primarily an IAT-hooking file-redirect mod (see "The IAT hooking pattern" below), but also exports one function, `Mad2LevelRedirect_GetCurrentLevel`, following the same resolve-by-name pattern as the other three; `mad2gameeffectsmod` is its only consumer today. See "Level redirection and current-level tracking" below for the full design.
- **`mad2hookutil`** (`mad2hookutil_api.h`, deployed as `aa_mad2hookutil.dll`) — the shared IAT/vtable-hooking primitives DLL; see "The IAT hooking pattern" below for what it exports and who consumes it. Does **not** follow the lazy-resolution pattern above: its `aa_` prefix (sorts-first, mirroring `zz_mad2graphicseffectmod.dll`'s sorts-last trick in reverse) guarantees it's the first `mad2/mods/*.dll` loaded, so consumers resolve it **synchronously from their own `DllMain`** (`GetModuleHandleA`/`GetProcAddress`, no lazy retry, no background thread) instead of waiting for a first per-frame hook call — IAT/vtable hooks have to be installed immediately at load, so a consumer's `DllMain` cannot defer resolving this dependency the way it can for `mad2xinput`/`mad2config`/`mad2effects`. Also exports `Mad2HookUtil_InstallInlineHook` — a standard 5-byte relative-JMP inline detour for an arbitrary internal function found by address (not reached via an import table or vtable), added for `mad2xdeltamod`'s `igIGZLoader::parseSections` hook (see `docs/IGA_FORMAT.md`). Unlike `PatchIat`/`PatchVTableSlot`, the caller supplies `stolenBytes` themselves (manually verified via disassembly) rather than it being auto-detected.
- **`mad2textrenderer`** (`mad2textrenderer_api.h`) — the shared GDI-text-to-texture rasterizer + D3D9 state save/restore + quad-drawing helper, factored out of what used to be 5 mods' worth of near-identical text-overlay boilerplate (`mad2igttimer`/`mad2playercoords`/`mad2inputdisplay`'s fixed-size single-line lists, `mad2effectshud`'s dynamically-resized list, `mad2twitchchat`'s per-run-colored/positioned runs). Unlike `mad2hookutil`, it **does** follow the ordinary lazy-resolution pattern (resolved on first `EndScene` call, same as `mad2xinput`) since nothing in it needs to run synchronously from another mod's `DllMain`.

### The IAT hooking pattern

File/IO-redirecting mods (`mad2assetloader`, `mad2saveloader`, `mad2levelredirectmod`) and `mad2xinput` use **Import Address Table patching**, not inline/trampoline hooking: for each currently-loaded module in the process (enumerated via `Toolhelp32Snapshot`), they walk its import directory and, for a given `(importDll, importName[, ordinal])`, overwrite the resolved function pointer in `FirstThunk` with their hook — matched against `OriginalFirstThunk` (the name thunk) since `FirstThunk` has already been overwritten with addresses by the loader. Every D3D9-hooking mod (see "D3D9 overlay hooking" below) also uses this same technique for its initial `Direct3DCreate9` hook, plus a related vtable-slot-overwrite technique (`PatchVTableSlot`) for `CreateDevice`/`EndScene`/etc.

- Both techniques' implementations now live in **one shared DLL, `mad2hookutil`** (`aa_mad2hookutil.dll` — see its own entry in "Shared-API mods" above for the naming/resolution story), not duplicated per mod. Confirmed via grep — no mod directory has its own `iat_hook.{h,cpp}` or inlined `PatchIat`/`PatchVTableSlot` anymore; every consumer instead includes `mad2hookutil_api.h`: `mad2assetloader`, `mad2saveloader`, and `mad2xinput` (via `mad2hookutil`'s ordinal-aware parameter — the one place the merge had to preserve a real behavioral difference between the old per-mod copies) for IAT patching; `mad2shadowfix`, `mad2levelredirectmod`, `mad2mirrormod`, and every D3D9-overlay mod (`mad2igttimer`, `mad2playercoords`, `mad2inputdisplay`, `mad2twitchchat`, `mad2effectshud`, `mad2graphicseffectmod`, `mad2musichud`) for both. This is a straight consolidation of what really was, historically, a near-identical copy duplicated across each of those source trees (`mad2assetloader/src/iat_hook.cpp` was the original, most-thoroughly-commented version, referenced when writing the merged implementation) — no per-mod inlined copy remains anywhere in the tree today.
- Hooking mods **chain onto whatever was in the IAT before them** via a `prevFunc` out-param, rather than resolving straight from the DLL that "really" owns the export. This is what lets multiple mods hooking the *same* import compose correctly regardless of `mad2/mods/` load order — the second one installed calls through to the first one's hook instead of clobbering it.
- `mad2shadowfix` hooks `Direct3DCreate9`/`Direct3DCreate9Ex` in `d3d9.dll` itself (after the real backend DLL — DXVK, wine3d, dxwrapper-chained, whatever — is already loaded and resolved by the normal loader), making it backend-agnostic instead of shipping a competing `d3d9.dll`. Every other D3D9-hooking mod follows the simpler variant of this (see below).
- `mad2levelredirectmod` and `mad2assetloader` both also IAT-hook `ntdll.dll`'s `NtCreateFile` (the native NT API `CreateFileA`/`W` are themselves built on), not just `kernel32.dll`'s `CreateFileA`/`CreateFileW` — for two independent reasons, discovered separately. `mad2levelredirectmod` added it first: direct instrumentation showed the game's level-archive streaming never goes through `CreateFileA`/`W` at all after boot, so its own slot→level redirect (see "Level redirection and current-level tracking" below) would silently never fire without it. `mad2assetloader` added the same hook later, for the same underlying reason but a different feature: its `Content/Streams/win/` → `Content/Streams/mod/` asset-override redirect already worked for ordinary assets opened via `CreateFileA`/`W` (e.g. `Content/Streams/mod/global.arc`), but was confirmed live in-game to silently miss `.bld` level archives specifically, which route through `NtCreateFile` the same way level-archive opens generally do. Both mods keep their `CreateFileA`/`W` hooks installed too, as a harmless defense-in-depth fallback, and both use the same `PatchIat`/`PatchIatAllModules` mechanism, just additionally pointed at `("ntdll.dll", "NtCreateFile")`. One real wrinkle `NtCreateFile` callers have to handle that `CreateFileA`/`W` callers never do: its `ObjectAttributes->ObjectName` can be relative to an already-open `ObjectAttributes->RootDirectory` handle instead of a fully-qualified path (e.g. just `"VolcanoRave.bld"`, no directory component at all). `mad2levelredirectmod`'s redirect tolerates this by construction — it never leaves the directory the handle is already scoped to, so a bare relative name substitution just works. `mad2assetloader`'s redirect needs to jump to a *sibling* directory (`win/` → `mod/`), which a bare relative name can't express on its own, so for that specific case (`RootDirectory` set, bare name, level-archive extension) it resolves the handle to its own absolute path via `GetFinalPathNameByHandleA` first, then converts back to the NT-native `\??\`-prefixed form (distinct from — and not directly interchangeable with — the superficially similar `\\?\` Win32-namespace prefix that API returns) before handing a fully-qualified replacement to the real `NtCreateFile`.

### Level redirection and current-level tracking

`mad2levelredirectmod` has two responsibilities, both driven by intercepting the game's level-archive opens (see the `NtCreateFile` note above):

1. **Redirection.** The external sibling project `../mad2rando5` computes a `Slot -> Level` mapping and writes it to `level_redirects.txt` (`Slot=Level` per line, `#` comments/blank lines ignored) in the game exe dir, rather than rewriting or symlinking archive files itself. This mod reads that file at startup and rewrites the requested archive name in each intercepted open to implement the redirect. With no `level_redirects.txt` present, it's a pure passthrough — randomization is opt-in.
2. **Current-level tracking.** `mad2gameeffectsmod`'s `PlayerTeleport` (needs a level-keyed coordinate pool) and `MangoMutate` (gated to levels with a mango counter) need to know the current level. The obvious source, `ScriptInfoLib.dll`'s `_levelLoadRequest` pointer, is only valid for a narrow window during an active load and was observed to work only intermittently. Instead, every intercepted level-archive open *is* the "level changed" event — and reports the actual content level rather than the requested slot, so it stays correct under redirection for free. Exposed as `Mad2LevelRedirect_GetCurrentLevel`; `mad2gameeffectsmod` prefers this and falls back to the `ScriptInfoLib` heuristic if `mad2levelredirectmod` isn't loaded.

Load order matters here in a way that falls out of the ordinary alphabetical sort without needing a `zz_`-style trick: `"mad2assetloader"` sorts before `"mad2levelredirectmod"`, so `mad2assetloader`'s hooks — including its own `NtCreateFile` hook, see "The IAT hooking pattern" above — install first and this mod's install second, becoming the outer hook (the one the engine actually calls first on every intercepted open, chaining inward to `mad2assetloader`'s hook and finally the real `NtCreateFile`). Renaming this mod to sort earlier would flip that with nothing else enforcing the order.

### D3D9 overlay hooking, and why load order matters

`mad2igttimer`, `mad2playercoords`, `mad2inputdisplay`, `mad2twitchchat`, `mad2effectshud`, `mad2musichud`, and `mad2graphicseffectmod` all use the same three-step hook: IAT-hook `Direct3DCreate9` in `d3d9.dll` → on first call, vtable-patch `IDirect3D9::CreateDevice` (slot 16) → on first successful device creation, vtable-patch `IDirect3DDevice9::EndScene` (slot 42). (Only `mad2shadowfix` bothers with the `Ex` variant and a full COM proxy — see below; the simpler mods have worked fine without it.)

**Load order determines draw order, precisely**: whichever mod's `CreateDevice`/`EndScene` hook installs *last* overwrites the vtable slot last, so it's what the engine actually invokes first each frame; its own `RealEndScene` chains to whichever hook was there before (the previous mod, or eventually the true engine `EndScene`). So **the last-loaded D3D9-hooking mod draws first; the first-loaded one draws last** (closest to Present, "on top" for ordinary additive HUD draws). This composes transparently for every mod that just draws a small additive overlay — order genuinely doesn't matter for those.

It stops being transparent for `mad2graphicseffectmod`, whose effects pipeline **captures and destructively redraws the entire backbuffer** every frame it has an active effect (see below). Any mod that draws *before* that capture (i.e. any mod loaded *after* `mad2graphicseffectmod`, since later-loaded = drawn-first) gets its HUD baked into the captured frame and transformed right along with everything else. This was a real, observed bug — `mad2playercoords`/`mad2twitchchat` (alphabetically after `mad2graphicseffectmod`) had their overlays captured and warped, while `mad2igttimer`/`mad2inputdisplay`/`mad2effectshud` (alphabetically before) were unaffected. Fixed by renaming the deployed DLL to `zz_mad2graphicseffectmod.dll`: combined with `mod_loader.cpp`'s now-explicit alphabetical sort, this guarantees it's always the last mod loaded, so every other overlay mod is loaded (and thus hooked) earlier and draws safely after the transform. If you add a new D3D9-hooking mod, it does **not** need any special naming — this only matters for mods that destructively rewrite the whole backbuffer, which today is just `mad2graphicseffectmod`.

### `mad2shadowfix` in detail

Diagnostics + fix for a specific bug: on Linux D3D9 backends (DXVK, wine3d), the game's shadow pass bound its 1024×1024 `D3DFMT_R32F` render target/depth-stencil but issued zero draw calls — shadow casters were being culled CPU-side before any GPU work happened. It wraps the real `IDirect3DDevice9`/`IDirect3DQuery9` returned by the real `Direct3DCreate9(Ex)` in `ProxyDirect3DDevice9`/`ProxyQuery9` (full COM vtable forwarding wrappers) to intercept and selectively rewrite calls.

- **The actual fix** (`disableShadowAlphaTest`, on by default): the shadow-pass pixel shader alpha-tests every fragment (for hair/foliage cutouts); under DXVK/RADV that test fails for effectively every pixel, so draws "succeed" but the shadow map stays blank. The mod forces `D3DRS_ALPHATESTENABLE` off while the shadow render target is bound. Confirmed via `GetRenderTargetData` readback (100% zero pixels with it on, real depth variance off) and visually. Trade-off: cutout shadow casters render as solid silhouettes instead of correctly cut out.
- Shadow-pass detection is purely by render-target signature: `SetRenderTarget(0, ...)` checks if the surface is 1024×1024 `D3DFMT_R32F` to enter/exit `m_isShadowPass` state.
- Everything else in the file is **environment-variable-gated diagnostics or untested experiments** kept around for future investigation — shader-model version spoofing, vertex-shader-constant-count overrides, occlusion-query-result forcing, point-filter forcing on the shadow sampler, depth/slope bias scaling, GPU vendor/device spoofing, shader binary dumping to `shaders_dump/*.bin`, shadow-map texture readback dumping. All default off/no-op; see `Config`/`LoadConfig()` in `shadowfix.cpp` for the full list of `SHADOWFIX_*` env vars. Default log level is silent (`SHADOWFIX_LOG_LEVEL=0`) since per-call logging measurably hurt frame time during testing; set to `1` or `2` for diagnostics, or `SHADOWFIX_TRACE_SHADOW_PASS=1` for a low-noise trace of just what happens while the shadow RT is bound.
- Logs to `shadowfix.log` in the game's working directory (not the shared `mad2modloader.log`).

### `mad2mirrormod` in detail

"Mirror Mode" — horizontally flips the rendered frame and inverts the left/right analog stick X axis to match. Unlike everything in "The chaos-effects system" below, this is a **persistent, full-session toggle**, not a randomized/timed effect — it registers nothing with `mad2effects` and has no `Trigger`/duration concept. Config-driven (`[Mirror]` `Enabled` in `config.cfg`, seeded off) with an optional live `ToggleKey` hotkey to flip it mid-session.

- **Input half** needs no new hook at all — it's a pure consumer of `mad2xinput`'s existing layered-override system, adding one override layer with `invertLX`/`invertRX` set via `Mad2XInput_AddOverride`.
- **Visual half tries two techniques, in order, every session:**
  1. **Projection-matrix mirror (HUD-safe, tried first).** Hooks `SetTransform` (vtable slot 44) and `SetRenderState` (slot 57) in addition to the usual `EndScene`(42)/`Reset`(16) pair — all four indices verified directly against this toolchain's own `d3d9.h` interface declaration order, not recalled from memory. When the game calls `SetTransform(D3DTS_PROJECTION, matrix)` with something that looks like a real 3D perspective matrix (`_34 != 0` — true for a `D3DXMatrixPerspective*`-style matrix, false for an orthographic one, which is the conventional shape of a 2D HUD projection), it negates `_11` (the X-axis scale term) before passing it through. This mirrors the 3D world in clip space, before anything is rasterized — so 2D/screen-space HUD draws (a distinct orthographic `SetTransform` call, or `D3DFVF_XYZRHW` pretransformed vertices that skip the transform pipeline entirely) are never touched at all. A true mirror is orientation-reversing, which flips triangle winding as the rasterizer sees it, so `SetRenderState`'s `D3DRS_CULLMODE` also gets inverted (`CW`↔`CCW`) for as long as the currently-active projection is a mirrored one — otherwise every backface-culled object would render inside-out.
  2. **Full-backbuffer mirror (fallback).** Reuses `mad2graphicseffectmod`'s own `InvertX` technique verbatim (a screen-space quad with the left/right UV coordinates swapped) via the `EndScene`/`Reset` hook. This is the *only* technique used until/unless technique 1 actually fires — a `g_ProjectionTechniqueEngaged` latch flips permanently true the first time a perspective projection gets mirrored, and `HookEndScene` stops doing its own backbuffer flip from that frame on (running both at once would double-flip the image back to unmirrored). This fallback unavoidably also mirrors the game's own native HUD (already baked into the backbuffer by the time any mod's `EndScene` hook ever sees a frame) — but it's guaranteed to produce *some* correct mirror even if the game's main 3D pass turns out not to route through the fixed-function `D3DTS_PROJECTION` state at all (e.g. transforms set via vertex shader constants instead — technique 1 has no way to intercept that; reverse-engineering an unknown shader's constant-register layout well enough to safely rewrite it blind isn't attempted).
  - **`[Mirror]` `ForceBackbufferMirror`** config key forces technique 2 unconditionally, as an escape hatch if technique 1 turns out to misbehave for this specific game/engine (e.g. objects rendering inside-out from a culling-compensation mismatch).
  - **Technique 1 is currently disabled** (`kEnableProjectionTechnique = false`, top of the file's anonymous namespace) — two in-game playtests each still showed broken culling with the world not visibly mirrored, meaning the technique was very likely engaging on the wrong projection matrix (most likely `mad2shadowfix`'s own documented shadow pass) even after a render-target-signature check was added specifically to exclude that. The actual root cause hasn't been pinned down yet. Rather than delete the code, `kEnableProjectionTechnique` is the sole switch controlling whether `HookCreateDevice` installs the `SetTransform`/`SetRenderState` vtable hooks at all — with it `false`, mirror mode always uses technique 2 (the original, reliable, HUD-inclusive full-backbuffer flip) unconditionally, and none of technique 1's code ever runs. Flip it back to `true` to pick this up again.
- Deployed with a `zz_` prefix (sorting after every other overlay mod, right behind `zz_mad2graphicseffectmod` itself) so that even while stuck on the technique-2 fallback, every other project overlay (`mad2effectshud`, `mad2igttimer`, `mad2playercoords`, `mad2twitchchat`, `mad2musichud`) loads/hooks earlier and draws *after* the mirror, staying legible instead of also being flipped — see "D3D9 overlay hooking" above. Only the game's own built-in HUD elements are ever at risk of being mirrored, never another mad2 mod's own overlay.
- No mad2effects registration, no background chaos-mode interaction — `mad2chaosmod` cannot randomly trigger it.

### `mad2minigamemodefix` in detail

Fixes a real gameplay bug relevant to the randomizer: the game tracks a persistent, session-wide "minigame mode" flag (set by selecting a minigame slot from the main menu, or loading a minigame-only level; per the game's own logic, only ever cleared once another non-minigame level loads). In practice, any level that merely *references* code shared with a minigame — `Dam_Busters`/`IslandFever` borrowing `Soccer`'s kicking code, `FixThePlane` borrowing `Card_Match_Game`'s, `WooingGloria` borrowing `HungryHippo`'s, `RitesOfPassage` borrowing `RoP_MusicalChairs`'/`Minigame_HotDurian`'s — spawns the minigame start/quit front-end regardless of whether it's actually a minigame, making those story levels incompletable whenever minigame mode is still active from an earlier minigame. `DrMelmen` and `VolcanoRave` are worse still: they're legitimately *both* a story level and a minigame depending on this exact flag, so they need it force-cleared to reliably act as the story version.

**Finding the flag.** Static analysis dead-ended repeatedly (`Mad2.exe` turned out to already be unpacked — a side effect of a no-CD patch applied to make modding easier, not evidence of an active protector to defeat; UI text is never a literal string in any binary at all, since it's fully externalized to `.pak` language files; several native-code leads, e.g. `AlchemyCommonLib.dll`'s reflected `SwitchLevelMessage::gameState` enum, turned out unrelated — that one is `GAME_STATE_EXIT/RUNNING/SHUTDOWN`, plain process lifecycle). The fix came from `mad2climbprobe`'s live-object-naming scan (`docs/CLASS_SCHEMA.md`'s "Naming investigation" section already had the lead: *runtime-spawned* objects' `igNamedObject` name field — `*(this+8)` as a plain `char*` — resolves to a real readable string, unlike the same field on static file objects, which only ever yields small useless ordinals). Scanning all committed process memory for a live object whose name contains "minigame" surfaced one named exactly `"Minigame Launch Mode"`, a plain `OpCreateVariable`-family object owned by `ScriptInfoLib.dll`. A live memory diff (title screen vs. an active minigame) showed every byte of that object identical between the two states except a 4-byte field at `+0x24` — `0` at the title screen, `1` during an active minigame.

**The fix itself**, in `mad2minigamemodefix.cpp`: a background thread (no D3D9 hook needed) tracks the current level via the shared `mad2leveldetect.h` helper and continuously forces that `+0x24` field to `0` on every level *except* a small whitelist — `Minigame_HotDurian`, `RoP_MusicalChairs`, `Soccer`, `HungryHippo`, and the `DivingLocation_*` levels — hand-confirmed (by playing each one with the flag forced off) to blackscreen without it. Everything else either doesn't care (`Card_Match_Game`, golf, animal chess all work fine either way, and incidentally gain their story-mode goal display — like on Wii — instead of the minigame-only HUD once the flag stays off) or is actively fixed by it (`DrMelmen`/`VolcanoRave` reliably act as their story version; every level that merely references shared minigame code stops incorrectly spawning the minigame front-end). The whitelist match is a case-insensitive substring, not an exact archive name — deliberately, so it keeps working under `../mad2rando5`'s level redirection: `mad2leveldetect.h` (and `mad2levelredirectmod.dll` underneath it) reports the actual *content* level that got opened, not the requested slot, so the whitelist check is correct regardless of which slot a level was loaded into. (Confirmed directly during the investigation: redirecting `Soccer`'s slot to `IslandFever`'s content reproduces the exact same incorrectly-spawned front-end bug this mod fixes.)

The object's live memory address isn't stable across game launches, so the same scan technique `mad2climbprobe` used to find it in the first place (`FindMinigameLaunchModeObject()`, a direct port) runs again at runtime: once on first need, cached from then on, with a rate-limited (every 2s) re-scan if the cached address ever stops being safely readable (observed stable across many level loads in practice, but not guaranteed forever). Deliberately does **not** start scanning until `mad2leveldetect.h` reports a real level (i.e. skips the initial `"None"` state) — this DLL's `DllMain` runs extremely early, before `Mad2.exe`'s own entry point does, and running this same scan that early (while the process's memory layout is still churning heavily) reliably crashed the game on load during development; every manual test this fix is based on was performed well into a stable running session, so that's the point scanning now waits for. Config-driven (`[MinigameModeFix]` `Enabled` in `config.cfg`, seeded on).

### The chaos-effects system

A generic "chaos mod" registry-and-scheduler, split across eight mods so each piece stays focused:

- **`mad2effects`** — the registry every effect-providing mod registers into, and every effect-triggering mod (or a human, via the HUD) reads from. `Mad2Effects_Register(desc)` takes a name, display name, a **chance `weight` that `mad2effects` itself never interprets** (purely metadata for whoever builds a weighted pool — today that's `mad2chaosmod`), an `apply`/`clear` callback pair, and a default duration range (both callbacks run on whatever thread calls `Trigger`/the internal ticker — not necessarily the render thread — so they must be safe off-thread and non-blocking). `Mad2Effects_Trigger(name, durationOverride)` calls `apply` and, if the effect has a `clear` callback, schedules an internal ticker thread (75ms poll) to auto-call `clear` after the duration expires; re-triggering an already-active effect just re-applies and resets the clear timer — **it does not stack**, so any effect-providing mod that randomizes a parameter each trigger must remove its own previous state before applying new state (see `mad2inputeffectsmod`'s `ReplaceOverride` helper) or effects silently accumulate across re-triggers (a real bug: this is exactly what caused `JoystickReversal` to intermittently feel un-reversed — two inverts left active at once cancel out). `Mad2Effects_SetDisplayName` lets an effect update its own live display text (e.g. `StickDirectionDisable` shows which stick+direction got picked this trigger) without touching its active/duration state.
- **`mad2inputeffectsmod`** — registers 10 XInput-based effects (`JoystickReversal`, `StickPercentLimit`, `SwapAB`, `SwapXY`, `RandomPressStart`/`RandomPressA`/`RandomPressB`/`PressY`/`PressX` — periodic phantom button presses, each spawning its own worker thread that pulses `forceHoldButtons` at a randomized interval, stoppable via a manual-reset event — and `StickDirectionDisable`, which picks a random stick+direction and blocks it, explicitly non-stacking with itself). Has no D3D9 hook of its own, so instead of the usual "resolve dependencies lazily from the first `EndScene` call" pattern, it uses an **init-only background thread**: `DllMain` spawns a thread that retries with a short sleep until `mad2config`/`mad2xinput`/`mad2effects` are all resolvable, then registers every effect and exits.
- **`mad2graphicseffectmod`** (deployed as `zz_mad2graphicseffectmod.dll` — see "D3D9 overlay hooking" above for why) — ~19 screen-space post-process effects (rotate, zoom, pulse, pixelate, invert X/Y, chromatic aberration, deep fry, vignette, sine-wave displacement, kaleidoscope, screen melt, frame echo/blur, 3fps cap, and more) chained through a ping-pong offscreen-texture pipeline in `EndScene`: capture the backbuffer once, then run each *currently active* effect's render function in sequence (source = previous stage's output, destination = the other ping-pong texture, or the real backbuffer for the last effect in the chain), so however many effects chaos mode happens to have simultaneously active compose correctly. Everything is built from **D3D9 fixed-function techniques only** — no pixel shaders, no D3DX (unreliable under Proton/Wine — no redistributable guaranteed present; see `mad2shadowfix`/`mad2igttimer`'s precedent) — including some genuinely clever ones: affine transforms (rotate/zoom/pulse) via a single quad with a custom UV at each of its 4 corners (mathematically *exact*, not approximate, because `D3DFVF_XYZRHW` vertices skip the perspective divide); non-affine warps (sine displacement, melt, kaleidoscope) via many small hand-tessellated quads/wedges; per-channel isolation via `D3DRS_COLORWRITEENABLE` masking across multiple passes; downsample-then-point-filter-upsample for pixelation; a procedurally-baked radial gradient texture multiply-blended for vignette; a persistent accumulation texture alpha-blended each frame for echo. Three effects are **deliberate reinterpretations**, not literal implementations, because a faithful version needs true per-pixel cross-channel math (grayscale luminance, channel permutation) that plain D3D9 fixed-function genuinely cannot do without unacceptable quality loss (verified by hand-deriving the `D3DTOP_DOTPRODUCT3` math, which crushes shadow detail badly) — see the file header for exactly what "Gameboy palette", "Mixup RGB channels", and "Thermal Inversion" actually do instead. A "Wireframe" effect (forcing `D3DRS_FILLMODE=WIREFRAME`) was attempted and removed: it had no visible effect on the game's own rendering, almost certainly because the game resets that state itself as part of its own per-draw setup — doing it properly would need intercepting `SetRenderState` itself, which the mod didn't do at the time. Every effect's render function must reset `D3DRS_COLORWRITEENABLE` to full at its own start (not just at the end) since multiple effects' passes run back-to-back within one frame and a channel-masking effect earlier in the chain would otherwise leak its restricted mask into the next effect.
  - **`InvertedCulling` ("Inside-Out World")** is a 20th effect, and structurally different from the other 19: it's not a post-process pipeline stage at all (no `RenderFn`, never in `g_Pipeline`) — it hooks `SetRenderState` (vtable slot 57) directly and inverts whatever `D3DRS_CULLMODE` the game asks for while active, so backface-culled geometry renders inside-out with holes where solid surfaces should be. It exists because it's *exactly* the bug that showed up in `mad2mirrormod` while building that mod's HUD-preserving projection-mirroring technique (mirroring flips triangle winding; forgetting to compensate cull mode produces precisely this look) — turned into a real chaos effect once it turned out to look genuinely striking on its own, not just a fix. See `mad2mirrormod`'s own section below for the actual story/fix.
- **`mad2chaosmod`** — no D3D9 hook, just a background director thread. Reads `[ChaosMode]` config once at startup (`Enabled`, default `false`; `MinIntervalSeconds`/`MaxIntervalSeconds`, default `5`/`15`); if enabled, loops forever picking a randomized interval, building a weighted "ticket pool" from every registered effect's weight (with an optional per-effect `Weight_<EffectName>` override in `config.cfg`, read fresh each cycle), and calling `Mad2Effects_Trigger` on the winner. Conceptually ports the same ticket-pool director-loop design as the external `../mad2mod` reference tool (design only, not shared code).
- **`mad2effectshud`** — D3D9 overlay, bottom-right by default, listing the display names of every currently-active effect (queried from `mad2effects` every frame via `GetCount`/`GetInfo(...).isActive`). Both a player/streamer-facing "what's happening to me right now" readout and a debugging aid — the text texture is only rebuilt when the active list's content actually changes. Inherits the same "can get captured by `mad2graphicseffectmod`'s pipeline if load order is wrong" caveat as any other overlay mod, mitigated by the `zz_` prefix fix above.
- **`mad2companionmod`** — registers three effects, all with no auto-revert duration (stay active until explicitly cleared, per `mad2effects_api.h`'s contract):
  - `SM64Challenge` (`sm64mod.cpp`) — launches a separate Super Mario 64 process (the vendored `extern/sm64ex-alo`), blocks Mad2's own controller input via `mad2xinput`, and streams `mad2xinput`'s **post-override** state (`Mad2XInput_GetOverriddenState` — so an active `JoystickReversal`/`SwapAB`/etc. effect also applies inside SM64) to it over a loopback UDP socket. SM64 can't run inside the same Wine process as Mad2 (would stack two D3D9 translation layers), so under Wine this mod never launches anything itself — it sends a `LAUNCH` control packet to `mad2relauncher` (see below), which forks the native Linux SM64 binary and handles window-focus juggling via X11; on real Windows it launches a Windows-built `sm64.exe` directly via `CreateProcess` instead.
  - `JakChallenge` (`jak1mod.cpp`) — the same shape, targeting the vendored OpenGOAL `extern/jak-project` (`gk`) instead: Wine-only. Investigated whether upstream `open-goal/jak-project` supports a native Windows build at all (its README states x86_64 Windows support, and its CI has dedicated `windows-build-clang`/`windows-build-msvc` workflows) — confirmed it does, but only via Visual Studio/MSVC SDKs or Windows-native clang, **no MinGW cross-compile path at all**, unlike every other Windows target in this repo (which all cross-compile from Linux via `i686-w64-mingw32`). That's a fundamentally different toolchain requiring an actual Windows build machine, not achievable from this repo's Linux cross-compile setup — treated the same as SM64/Jak1's "don't force it" precedent and left Wine-only; `ApplyJakChallenge` still explicitly no-ops with a log line on real Windows. Sends `mad2relauncher` a `LAUNCH` packet over its own loopback UDP port (distinct magic/ports from SM64's, see `include/mad2jak1_protocol.h`). One real difference: `gk` has no socket primitive of its own (only its GOAL script source is available to patch, and GOAL has no socket API), so `jak1mod.cpp` translates XInput state to PS2 hw-cpad wire format itself (`XInputToPs2Pad`) before sending — `mad2relauncher` and a hand-written patch in `goal_src/jak1/engine/ps2/pad.gc`'s `service-cpads` just relay/copy the already-translated bytes into the game via a polled file (`mad2_input.dat`), rather than decoding on the receiving end like SM64's `controller_udp.c` does.
  - `MarioLegacyChallenge` (`mariolegacymod.cpp`) — the same shape again, targeting the vendored *separate* jak-project fork `extern/mario-legacy` (`gk`, `OpenGOAL-Mods/Super-Mario-Legacy`) instead of `extern/jak-project`. Unlike `JakChallenge`, this one DOES have a native-Windows branch: `OpenGOAL-Mods/Super-Mario-Legacy`'s GitHub releases already ship prebuilt `gk.exe`/`goalc.exe`/`extractor.exe` for the same tag (v0.0.28) already vendored, sharing a confirmed-byte-identical `data/` asset tree with the Linux binaries — so no build step was needed, just vendoring the three `.exe` files into `extern/mario-legacy/` alongside the existing Linux ones. On real Windows, `ApplyMarioLegacyChallenge` launches `gk.exe` directly via `CreateProcess` (same shape as `SM64Challenge`'s native branch) and best-effort-focuses its "OpenGOAL"-titled window; under Wine it still goes through `mad2relauncher` as before. One real difference from SM64's native branch: `gk` has no socket primitive at all (same as Jak1), so instead of streaming UDP directly to the child process, the native-Windows branch itself atomically writes the polled `mad2_input.dat` file (`WriteInputFileAtomic`, mirroring what `mad2relauncher/mariolegacy.go` does on the Wine side) that the same `pad.gc` patch below already polls every frame — no new GOAL-side code needed for either platform. Own loopback UDP ports/magic (`include/mad2mariolegacy_protocol.h`, used only on the Wine branch now). This fork's `engine/ps2/pad.gc` was confirmed byte-identical to `extern/jak-project`'s own aside from the injection patch itself — Mario's moveset reads buttons through the same PS2 pad-buttons bitfield via `cpad-hold?`/`cpad-pressed?`, so `mariolegacymod.cpp`'s `XInputToPs2Pad` is the same translation as `jak1mod.cpp`'s (duplicated, not shared — the two source files' copies operate on distinct nominal packet types). One real, live-discovered difference from Jak1: this fork's release layout nests `goal_src`/assets under a `data/` subdirectory, so its GOAL file-stream opens (and thus the injection file, on both platforms) resolve under `<extern/mario-legacy>/data/mad2_input.dat`, not the repo root like `extern/jak-project`'s. **Known gap**: unlike `extern/jak-project`, this fork's `game-info.gc`/`level.gc`/`kernel-defs.gc` do not carry our title-screen-skip / `*kernel-boot-level*` patch (diffed live — genuinely absent upstream), so `-level`/`-boot -fakeiso` currently boots to this fork's own title screen rather than jumping straight into a checkpoint like JakChallenge does, on both platforms; porting that patch into this fork's differently-structured `game-info.gc` is a follow-up, not done yet. For the same reason it also has no JakChallenge-style auto-exit-on-power-cell behavior — it only self-clears when the player quits `gk` manually, like SM64Challenge.

  All three effects: no D3D9 hook of their own -- use the same init-only background thread pattern as `mad2inputeffectsmod`. A watcher thread notices the child process actually exiting and self-clears the effect via `Mad2Effects_ClearByName`, arbitrated against externally-triggered clears (re-roll, `ClearAll`, re-trigger) so teardown only runs once. `JakChallenge` additionally self-exits when the player collects a power cell, via a hand patch in `extern/jak-project/goal_src/jak1/engine/game/game-info.gc` that calls `(kernel-shutdown)` while `*kernel-boot-level*` is set (always true for our `-level <checkpoint>` boot) — `MarioLegacyChallenge` does not have this yet, see above.
- **`mad2podcastmod`** — registers one effect, `PodcastBreak`, same "no auto-revert duration, self-clearing watcher thread" shape as `mad2companionmod`'s `SM64Challenge`. Unlike `mad2companionmod`, `PodcastBreak` itself never launches or kills anything as part of triggering the effect: `mad2music` is expected to already be running continuously for the whole session, so `ApplyPodcastBreak`/`ClearPodcastBreak` just send a one-shot `TRIGGER` packet over loopback UDP asking it to play a random spoken-word clip (ducking the looping background music underneath it) and wait for a `FINISHED` reply to self-clear. Separately from the effect itself, this mod's init thread has a **native-Windows-only startup step** (`StartMad2MusicIfNeeded_NativeWindows`) since there's no `mad2relauncher` there to supervise `mad2music` the way it does under Wine (see below): checks a named mutex `mad2music.exe` holds for its whole process lifetime (`Mad2Music_SingleInstanceMutex`, created in `mad2music/src/main.cpp`'s `main()`) via `OpenMutexA`, and `CreateProcess`'s it once if not already running, then leaves it running unsupervised for the session (no crash-relaunch — nothing on native Windows provides that yet). Configurable via `[Podcast]` `WindowsMusicPath`/`WindowsAudioDir` (both relative to the game exe dir, no deploy target wires them up automatically yet — a manual placement step, same status as `mad2companionmod`'s `WindowsXxxPath` keys).
- **`mad2gameeffectsmod`** — registers three one-shot, no-`Clear`-callback effects ported from `../mad2mod`'s external overlay tool: `ObjectShuffle` (Fisher-Yates shuffles the positions of every Havok physics object found on the heap, player excluded), `MangoMutate` (randomizes the player's mango count, gated to levels that actually display one), and `PlayerTeleport` (teleports the player to a random previously-logged coordinate from `data/coordinates.yaml`, deployed alongside the mod, filtered to the current level). Runs entirely in-process (a plain pointer dereference where `../mad2mod` needed `process_vm_readv`/`writev` as a separate process), gating every pointer hop through an `IsPlausiblePointer()` check. Depends on `mad2levelredirectmod` for current-level detection (see above). Same init-only background thread pattern as the other no-D3D9-hook effect mods.
- **`mad2nesmod`** (`src/nesmod.cpp`) — structurally different from every other companion-process-style effect above: instead of spawning a separate emulator/engine process (`mad2companionmod`'s pattern, requiring native-Linux orchestration via `mad2relauncher` under Wine), it `LoadLibraryA`s prebuilt **libretro cores** (fceumm for NES/FDS, a 32-bit Windows DLL fetched by `just fetch-libretro-fceumm` into `extern/.libretro-cores/`; mupen64plus_next for N64, fetched by `just fetch-libretro-mupen64plus` — both matching this mod's own 32-bit i686 MinGW build) directly inside the Mad2 process and hand-implements the handful of libretro frontend callbacks itself — no RetroArch, no separate frontend process at all. TWO independent core instances (an `Engine` struct, one per `System::Nes`/`System::N64`, see `g_Engines[2]`), each with its own loaded-game/audio/pixel-format state, since libretro cores are global C API state per loaded module and can't share one instance across different emulated systems the way `NesChallenge`/`NesLostLevelsChallenge` share the single FCEUmm instance. Registers one `mad2effects` effect per entry in its own `g_Games[]` catalog — `NesChallenge` (Super Mario Bros., ordinary cartridge ROM), `NesLostLevelsChallenge` (Super Mario Bros. 2 / The Lost Levels, a Famicom Disk System image), and `N64Sm64Challenge` (Super Mario 64, an actual N64 ROM dump emulated via mupen64plus_next — a separate effect from `mad2companionmod`'s own `SM64Challenge`, which instead runs the natively-built decompiled PC port as a whole separate process) as of this writing; `EnsureGameLoaded(gameIndex)` calls `retro_unload_game`/`retro_load_game` on that game's own engine to switch when a different game's effect triggers while one is active (only within the same engine — the other engine's dormant loaded game, if any, is untouched), and `ApplyEmuGame` explicitly clears the outgoing game's own effect first so `mad2effects`' `isActive` bookkeeping (and `mad2effectshud`) never shows more than one as active simultaneously. Each registered effect has the same "no auto-revert duration, stays active until explicitly cleared" contract as `SM64Challenge`, but Clear only **pauses** (flips a flag, un-blocks Mad2's input) rather than tearing anything down — the core and its loaded ROM stay resident, so a re-trigger of the *same* game resumes exactly where the player left off (an option `mad2companionmod`'s effects don't have, since their state lives in a process that gets killed on Clear); switching to a *different* game (same engine or the other one) does fully reload it. Has its own D3D9 `EndScene` hook (same IAT/vtable-patch technique as `mad2igttimer`, via `aa_mad2hookutil.dll`) that calls `retro_run()` once per frame on whichever engine is currently ACTIVE — synchronously, always from the render thread, so that engine's `video_refresh_cb` can write straight into a shared `D3DPOOL_MANAGED` texture with no cross-thread synchronization anywhere in the mod — then draws that texture as one full-screen, opaque, **nearest-neighbor-filtered** quad (a small hand-written draw function, `DrawEmuQuadPointFiltered` — deliberately not `mad2textrenderer.dll`'s shared `DrawTexturedQuad`, which hardcodes bilinear filtering, wrong for upscaled pixel art), completely replacing Mad2's own frame. Input is read directly from `mad2xinput`'s raw (pre-override) state, same lesson `SM64Challenge`/`JakChallenge` already learned about `GetOverriddenState` reading back your own just-applied input block (see `sm64mod.cpp`'s comment) — Mad2's own input is blocked via the same `AddOverride`-based technique while any of this mod's effects is active, with independently-configurable `UserIndex`/`BroadcastToAllControllers` per engine (`[Nes]`/`[N64]` config sections). Audio goes out through a small best-effort `winmm` `waveOut` ring buffer, one instance per engine (drops a frame's audio if every buffer is still busy rather than blocking the render thread). The vendored `libretro.h` (`mad2nesmod/include/`) is the official upstream header, included only for its struct/enum/constant definitions — every `retro_*` function is resolved by hand via `GetProcAddress` (`RETRO_IMPORT_SYMBOLS` is defined before including it specifically so the header's own `RETRO_API` declarations don't try to `dllexport` `retro_init` etc. out of *this* DLL). ROMs (`roms/smb1.nes`, `roms/smb2j.fds`, `roms/sm64.z64`, see `roms/README.md`) are user-supplied like `SM64Challenge`/`JakChallenge`'s ROM/ISO, but copied (not symlinked) into each deployed install's `nescore/`/`n64core/` folders by `justfile`'s `_deploy-nes`/`_deploy-n64` recipes, since they're read from inside the Wine-hosted Mad2 process itself rather than by a native Linux engine; the FDS game additionally needs a user-supplied `roms/disksys.rom` (the Famicom Disk System BIOS — copyrighted Nintendo firmware, never redistributed, same treatment as every other ROM/BIOS/ISO in this repo) staged alongside it, which FCEUmm finds itself via the `RETRO_ENVIRONMENT_GET_SYSTEM_DIRECTORY` callback (branched per-engine to return `"nescore"`/`"n64core"`, the same folders everything else for that system lands in).
  - **N64Sm64Challenge's renderer** is switchable via `[N64] Renderer` (`hardware`, default, or `software`). `hardware` bridges a real OpenGL context into this D3D9-only-hooked process for mupen64plus_next's default renderer, GLideN64: a hidden, never-shown window gives WGL somewhere to attach a pixel format (`EnsureN64GlContext`), the core renders into a dedicated offscreen FBO of the mod's own (`EnsureN64Fbo`, sized from the core's reported `max_width`/`max_height`, not resized again mid-session), and `VideoRefreshCb` reads it back via `glReadPixels` (detecting the `RETRO_HW_FRAME_BUFFER_VALID` sentinel) and uploads it into the same D3D9 texture the software cores' raw pixel buffers already go through — the draw/present path is fully shared and unaware which renderer produced a given frame. This turned out simpler than first feared: `mupen64plus_next`'s GL bridging goes through `glsm` (a shared libretro-common helper), whose own context-negotiation code (read directly from source, not guessed) requests a **plain compatibility-profile** `RETRO_HW_CONTEXT_OPENGL` context on this exact build (its own `CORE` macro isn't defined anywhere in the Makefile) — so a single old-school `wglCreateContext` call is enough, no `WGL_ARB_create_context` version/profile negotiation or dummy-context bootstrap. GL functions beyond 1.1 are resolved by hand via `wglGetProcAddress`, falling back to `GetProcAddress(opengl32.dll, ...)` for true 1.1 entry points, the standard Windows GL loader pattern. `software` instead force-answers the core's `"mupen64plus-rdp-plugin"` option with `"angrylion"` (a fully CPU-side RDP implementation confirmed, via the core's own Makefile, to always be compiled into Windows builds) before the core ever gets a chance to request a GL context at all — a real speed/accuracy tradeoff kept as a manual escape hatch. Getting `hardware` mode actually correct surfaced a whole *class* of bugs, all the same shape: several mupen64plus_next/GLideN64 core options are plain C globals at file scope with **no initializer** in the core's own `libretro.c`, so leaving `RETRO_ENVIRONMENT_GET_VARIABLE` unanswered for them (this mod's `EnvironmentCb` default for anything not explicitly forced) leaves them C-zero-initialized rather than falling back to their own *documented* default the way a full frontend presenting a real options UI would produce — discovered live, one crash/bug at a time, not anticipated up front: the R4300 CPU core defaulting to `Pure Interpreter` instead of `dynamic_recompiler` (near-unplayably slow, read as a hard-lock at first); requesting the RSP plugin `"hle"` while Angrylion is active silently substituting a second, independent CPU-side JIT (`Parallel RSP`, unrelated to the similarly-named Vulkan `ParaLLEl-RDP` project) that reliably crashed the process — fixed by requesting `"cxd4"` (Angrylion's traditional non-JIT pairing) directly instead; the left analog stick reading as permanently centered because `astick_sensitivity` (a percentage multiplier) zero-inits to 0, not its documented 100; and, once hardware rendering itself was working, N64 textures rendering as solid black inconsistently (some fine, some not) because GLideN64's own `MaxTxCacheSize` — whose own description literally reads *"Reduce it if you experience black textures leading to a crash"* — zero-inits to 0 cache elements instead of its documented 8000, alongside four boolean GLideN64 options (`EnableTextureCache`, `EnableLODEmulation`, `EnableShadersStorage`, `txFilterIgnoreBG`) found the same way via a script cross-checking every documented default in `core_options.h` against its C-variable initializer in `libretro.c`. All of the above are forced explicitly in `EnvironmentCb`'s `GET_VARIABLE` case now, in two parallel tables (`kHardwareVars`/`kSoftwareVars`) selected by `[N64] Renderer` — see the extensive in-code comments there for the full blow-by-blow. N64Sm64Challenge also has none of the NES games' RAM-poke tricks (`MuteMusic`/`RandomLevelStart`/`AutoStopOnLevelComplete`/FDS disk-swap auto-answer below) — those are SMB1/Lost-Levels-specific RAM addresses verified against those games' own disassemblies and don't generalize to an arbitrary N64 title; `RunAndDrawFrame` just runs and draws it, nothing more. A background-thread attempt at decoupling N64's `retro_run()` from Mad2's own render thread (to fix perceptible stutter during the software-only era) was tried and reverted after it reliably crashed Mad2.exe right after the first cross-thread `retro_run()` call, every time — leading theory is that mupen64plus_next's own internal "EmuThread" command-dispatch architecture isn't safe to drive from an arbitrary calling thread — so `retro_run()` stays synchronous on the render thread for both engines; see `nesmod.cpp`'s own comments for the full postmortem.
  - **N64 controller mapping** (`N64InputState`) is deliberately matched to mupen64plus_next's own default RetroPad-to-N64-pad translation (read directly from `custom/mupen64plus-core/plugin/emulate_game_controller_via_libretro.c` in the `libretro/mupen64plus-libretro-nx` upstream repo, not guessed): N64 A/B map to Xbox A/X by RetroPad *position* convention (RetroPad mirrors SNES-style B=bottom/Y=left face-button naming, so RetroPad B = Xbox A and RetroPad Y = Xbox X), Z trigger maps to the analog Left Trigger, L/R shoulders to Xbox LB/RB, the control stick to the left analog stick, and the C-buttons to the right analog stick (read via `RETRO_DEVICE_ANALOG`, not the D-Pad IDs, which the core reserves for the N64 pad's actual D-Pad) — with the Y-axis sign on both sticks inverted relative to XInput's own convention, derived (not guessed) from that same upstream source file's `inputGetKeys_reuse`. Flagged in-code as a first pass, not yet confirmed against actual in-game feel.
  Beyond just launching, this mod also directly manipulates the running game's own RAM each frame (via `retro_get_memory_data(RETRO_MEMORY_SYSTEM_RAM)`) at addresses verified against BOTH games' own disassemblies — SMB1's canonical `SMBDIS.ASM` by doppelganger, and Lost Levels' `SMB2J DISASSEMBLY` (`threecreepio/smb2j-disassembly` on GitHub, a ca65 port of doppelganger's original) — fetched and grepped for the exact label definitions rather than trusted from memory or "these games are similar" alone. Every address (`OperMode`, `WorldNumber`/`LevelNumber`/`AreaNumber`, the music-queue/buffer bytes) came back byte-identical between the two, which the two disassemblies' shared authorship and near-identical engine explains but doesn't by itself guarantee — checked independently rather than assumed:
  - **Level-complete auto-stop** (`AutoStopOnLevelComplete`, default on) — watches `OperMode`/`WorldNumber`/`LevelNumber`; when `OperMode` stays in GameMode continuously but `(World, Level)` changes, that's a level just being beaten and advanced past, and the active effect auto-clears (pauses) right there instead of continuing into the next level.
  - **Music-only mute** (`MuteMusic`, default off, live-toggle key `MuteMusicToggleKey`/F6) — silences the music engine while sound effects keep playing, using the game's own real "Silence" music track (both disassemblies' `Silence` constant, also used by the game itself at flagpole grabs/pipe warps) for exactly one frame per "something new is trying to play" event, then flattening the four music-state RAM bytes to plain 0 to fully disengage the music engine's per-frame APU writes. This two-step shape (real cutoff once, then go dormant) is deliberate, not incidental — holding the Silence *track* continuously (an earlier version of this did) also actively re-writes the Square 1 APU channel every single frame, which collides with and silences the jump sound effect (also Square 1) right along with the music; going dormant afterward stops touching the APU at all once things are actually quiet, so it stops fighting Square-1-channel sound effects. Un-muting re-requests the exact track that was interrupted through the game's own "start this area track" path (`AreaMusicQueue`) rather than poking its "currently playing" buffer directly and hoping unverified internal note-position state survived being muted — restarts the track rather than resuming mid-note, a deliberate safer tradeoff.
  - **Random level start** (`RandomLevelStart`, default on) — the "start the game at a random level" ask, at full World 1-8 / Level 1-4 granularity (not just a random world's first level, an earlier, more conservative version of this): the first time a game is freshly (re)loaded into the core, forces `WorldNumber`/`LevelNumber`/`AreaNumber` (while `OperMode` is still the title screen, so it's whatever's in effect when Start gets pressed) to a random world+level. Full-level granularity specifically depends on `AreaNumber` (the internal index `FindAreaPointer` actually uses to load an area, distinct from the displayed `WorldNumber`/`LevelNumber` "dash number") staying in lockstep with `LevelNumber` for the ordinary progression — confirmed directly from both disassemblies, not assumed: both reset to 0 together at world start (title screen, warp zone, post-castle world-advance all pair `sta AreaNumber`/`sta LevelNumber`) and both increment together by exactly 1 on every flagpole clear (`PlayerEndLevel`'s `inc LevelNumber` immediately followed by `NextArea`'s `inc AreaNumber`). Underground/pipe-detour sub-areas (e.g. World 1's hidden room in 1-2) never touch `AreaNumber`/`LevelNumber` at all — they use a completely different, per-level-embedded mechanism (a "row `$0e`" object-data entry that overwrites `AreaPointer` directly, gated to the current `WorldNumber` so the same room graphics can be reused across worlds — see `ParseRow0e`/`CheckFrenzyBuffer`), which is exactly why the naive "5 area-table entries but only 4 displayed levels per world" count doesn't actually complicate a direct level warp the way an earlier, more cautious version of this feature assumed. World count is per-game (`NesGame::worldCount`), currently **8 for both games** — Lost Levels' World 9 was tried and is now deliberately pinned back out of the pool (see below), not exposed at 9 the way it briefly was.
  - **Lost Levels' World 9 / "Worlds A-D" — parked, known broken.** World 9 itself (`World9Areas` sitting in the same `AreaAddrOffsets` table as every World 1-8 entry — `EndWorld1Thru7`'s own code just pins `WorldNumber` at 8 forever once reached, "make world 9 loop forever") looked like ordinary already-resident data, and the harder "Worlds A-D" repeat-loops (real players unlock these by beating the game 8 times) looked reachable too by forcing `HardWorldFlag` ($07fb) — confirmed from `GameMenuRoutine`/`InitializeArea` in `smb2main.asm` that the flag alone (not a different `WorldNumber`) is what makes `InitializeArea` force hard-mode enemy behavior and makes `LoadHardWorlds` pull in a genuinely different FDS-resident file ("SM2DATA4", `FileListNumber` 3). Getting there also surfaced a real, separate bug affecting ordinary play: any FDS file reload drives `DiskIOTask` through a `WaitForEject`/`WaitForReinsert` step that polls for a disk toggle FCEUmm ties to the `RETRO_DEVICE_ID_JOYPAD_R` button (`libretro.c`'s `retro_run`) — this mod's fixed pad mapping never produces that button, so it's fixed via `ApplyFdsDiskSwapAutoAnswer`, which synthesizes exactly one such press each time `DiskIOTask` freshly enters state 2 or 3 (a `g_FdsRPulseThisFrame` flag `InputStateCb` reads, separate from the real controller). Even after that fix and after narrowing `HardWorldFlag`'s forcing window to only engage once `OperMode_Task` ($0772) reaches 5 (`HardWorldsCheckpoint`, not from the moment the title screen appears like `WorldNumber`/`LevelNumber`/`AreaNumber` — forcing it earlier holds the game in a state real play never exercises), World 9 still black-screens on Start — confirmed via `TraceFdsStateTransitions` (added specifically to pin this down: logs every change to `OperMode`/`OperMode_Task`/`DiskIOTask`/`HardWorldFlag`, not just the disk-swap states) that the RAM-traced state machine completes the *exact same* "load finished, screen re-enabled" sequence (`OperMode_Task` reaching 2 within `GameMode`, the point `SecondaryGameSetup` clears `DisableScreenFlag`) that Worlds 1-8 complete successfully — live-tested identically **with HardWorldFlag forced on and with it left off**, both still black. Since it fails the same way either way, the problem isn't `HardWorldFlag`/"Worlds A-D" specifically — something about World 9 itself (its level data, or some other state a legitimate 8-world playthrough sets up that a direct warp skips) is broken, and RAM-state tracing alone can't see far enough to say what; would need actual visibility into the rendered output to take further. `NesGame::worldCount`/`supportsHardWorlds` are the switches to flip back on for whoever picks this up — the tracing/auto-answer machinery above is left in place, not reverted. `IncludeHardWorlds`/`DebugForceHardWorld` are currently inert either way.
    Getting this working surfaced a real, previously-latent bug affecting *ordinary* Lost Levels play too, not just Worlds A-D: any FDS file reload (Worlds 5-8's own `LoadWorlds5Thru8`, not just `LoadHardWorlds`) drives the SAME `DiskIOTask` state machine through a `WaitForEject`/`WaitForReinsert` step, which polls `FDS_DRIVE_STATUS` waiting for the player to physically toggle the virtual disk. FCEUmm ties that toggle to the player pressing the `RETRO_DEVICE_ID_JOYPAD_R` button while `GameInfo->type == GIT_FDS` (`libretro.c`'s own `retro_run`, read directly from the FCEUmm source, not assumed) — nothing in this mod's fixed XInput-to-NES-pad mapping ever produces that button, so left alone, the game would sit on a black "swap disk" screen forever the instant a player reached World 5, waiting for an input that could never come. Fixed by `ApplyFdsDiskSwapAutoAnswer`: watches `DiskIOTask` ($07fc) itself and synthesizes exactly one `JOYPAD_R` press (via a `g_FdsRPulseThisFrame` flag `InputStateCb` reads, entirely separate from the real controller) each time it freshly enters `WaitForEject`(2) or `WaitForReinsert`(3) — confirmed the same two state indices are shared identically across all four of this game's `DiskIOTask` dispatchers (`AttractModeDiskRoutines`/`GameModeDiskRoutines`/`VictoryModeDiskRoutines`/`HardWorldsCheckpoint`, each just swapping in a different "what to load" step at index 1). The actual file read itself (`LoadFiles`/`FDSBIOS_LOADFILES`) already succeeds without any of this, since FCEUmm's virtual disk is considered continuously "inserted" for the whole session unless something explicitly ejects it — only the wait-for-a-swap-that-never-comes UI step was ever at risk of hanging.
  - **`RefreshGameKey`/R** — force-reloads whichever game is currently resident in the core and activates it, re-rolling `RandomLevelStart`/`IncludeHardWorlds` exactly like a full Mad2 restart would rather than resuming where you left off (unlike `TestClearKey`/`TestTriggerKey`'s pause/resume, which deliberately leaves the loaded ROM's state alone) — added specifically so `RandomLevelStart`+`IncludeHardWorlds` (a ~1-in-18-per-load shot at a hard world) can be iterated on quickly without actually relaunching Mad2 each time. Defaults to the letter `R`, not an F-key — every single F1-F12 is already claimed by some other mod in this repo, several of them dev-only diagnostics that fire unconditionally on any keypress (confirmed live: an earlier `F4` default double-fired `mad2metadumper`'s full reflection dump alongside every press).
  - **`DebugForceWorld`/`DebugForceLevel`/`DebugForceHardWorld`** (all default off/0) — bypass `RandomLevelStart`'s RNG entirely and pin every fresh load to one exact world/level/hard-world-or-not combination, for deterministically re-testing one specific spot (with `RefreshGameKey`) instead of waiting on random luck.
  - HardWorldFlag's forcing window is narrower than WorldNumber/LevelNumber/AreaNumber's: only applied once `OperMode_Task` ($0772) reaches 5 (`HardWorldsCheckpoint`, the dispatch step that actually runs `LoadHardWorlds` — `AttractModeSubs`' own 6-step table: 0=`AttractModeDiskRoutines`, 1=`InitializeGame`, 2=`ScreenRoutines`, 3=`PrimaryGameSetup`, 4=`GameMenuRoutine`, 5=`HardWorldsCheckpoint`), not from the moment the title screen appears like the other three. `GameMenuRoutine` (task 4) is what processes the actual Start press and is where the title screen sits waiting the whole time beforehand — forcing `HardWorldFlag` that early would hold the game in a state (hard-world flag set while still merely deciding whether to start) real play and the original developers never exercise. First live test of a hard-world run black-screened on Start; this narrower timing is a plausible contributing fix, not a confirmed one — `FDSBIOS_LOADFILES` itself (the actual FDS-BIOS-level file loader `LoadHardWorlds` calls into) lives in the Nintendo-provided `disksys.rom` BIOS, not the game ROM, so it isn't in either disassembly and its internals can't be traced the way everything else here was.
- **`mad2twitchcontrolsmod`** — separate from `mad2twitchchat` (read-only chat overlay, anonymous IRC — see "Other overlay mods" above). Channel-point redemptions require an *authenticated* connection, so this mod instead speaks Twitch's EventSub protocol over a WebSocket (connect `wss://eventsub.wss.twitch.tv/ws`, receive `session_welcome` with a session id, POST to `https://api.twitch.tv/helix/eventsub/subscriptions` to subscribe `channel.channel_points_custom_reward_redemption.add`, then react to `notification` messages) using **WinHTTP**, not Winsock — verified working under this repo's actual Proton target via a standalone connectivity spike before the mod was built, since WinHTTP's WebSocket-over-TLS path was unproven here (only plain-Winsock `mad2twitchchat` was proven). Credentials (`OAuthToken`/`ClientId`/`BroadcasterUserId`) are pasted manually into `config.cfg` by the user (externally-registered Twitch app, no in-mod OAuth flow); reward titles map to `mad2effects` effect names via numbered `Reward<N>`/`Effect<N>` config keys (not a packed list — `mad2config`'s file format is strictly single-line-per-key). JSON is hand-parsed via small substring scans (no vendored JSON library, consistent with `mad2config`'s own precedent), which is fragile to any Twitch payload-shape change but accepted for the same "not worth a dependency for something this small" reasoning.

### Native Linux companion processes

Four pieces run outside the Wine process, launched/orchestrated by `justfile` rather than loaded as game-process DLLs:

- **`mad2relauncher`** — a Go shim that `justfile`'s `_play` recipe (and `mad2launcher/launch.go`'s own hand-duplicated equivalent) execs *instead of* invoking `umu-run`/gamescope directly, so it runs inside the same gamescope instance as `Mad2.exe`. Five jobs: (1) **crash relaunch** (`gameloop.go`) — keeps `umu-run <exe>` running, relaunching it on every exit until stopped via a global X11 `Ctrl+Q` hotkey, SIGTERM, or gamescope's own parent process dying (`parentwatch.go`'s `PR_SET_PDEATHSIG`) or its nested X11 display disappearing (`x11.go`'s `GrabStopKey` treats a closed X11 connection the same as the stop-key); (2) **SM64 orchestration** (`sm64.go`) — listens on a loopback UDP control port for `LAUNCH`/`STOP` requests from `mad2companionmod.dll`'s `SM64Challenge` effect (running inside Wine), forks the native Linux `extern/sm64ex-alo` binary, and does window-focus juggling via X11; (3) **Jak1 orchestration** (`jak1.go`) — same shape as (2) for `mad2companionmod`'s `JakChallenge` effect, forking `extern/jak-project`'s `gk` instead; additionally the actual UDP receiving endpoint for streamed controller input (`gk` has no socket primitive — see `jak1.go`'s file header), bridging it into `gk` via a polled file; (3b) **Mario Legacy orchestration** (`mariolegacy.go`) — `MarioLegacyController` is `Jak1Controller`'s exact twin for the separate vendored fork `extern/mario-legacy`, same file-bridge mechanism, own UDP ports (its polled input file lives one level deeper, `<extern/mario-legacy>/data/mad2_input.dat` — see `mad2companionmod`'s own bullet above for why); (4) **music/podcast supervision** (`music.go`) — starts the native `mad2music` binary once alongside the game and keeps it running/relaunched for the whole session (same crash-relaunch shape as the game itself); `mad2podcastmod` talks directly to `mad2music`'s own UDP control port, so `mad2relauncher` has no protocol role there beyond process supervision. Every child process (game, SM64, Jak1, Mario Legacy, music) is launched with both its own process group (so `Stop()`/`StopAll()` can signal its whole subtree at once) and `Pdeathsig` set (kernel-level guarantee it's killed if `mad2relauncher` itself ever dies outright, independent of whether its own graceful-shutdown code gets a chance to run).
- **`mad2music`** — a native Linux C++/SDL3 executable (own `CMakeLists.txt`, not part of the root MinGW cross-build — see Build commands above), ported from `../mad2mod`'s audio subsystem. Runs with cwd set to the game install directory (so `config.cfg`/`mad2music.log` land alongside every other mod's), but its audio pool (`-audio-dir`) lives outside any single install since it's shared across `mad2`/`mad2russia`/`mad2demo`. Two channels: background music (slot 0) loops continuously from a pool; podcast (slot 1) is driven externally, triggered by `mad2podcastmod.dll` sending a `TRIGGER` packet over loopback UDP and ducking the background music underneath it while it plays. Also cross-builds for native Windows (`just build-music-windows`, i686-w64-mingw32 + a fetched SDL3-devel-mingw release — SDL3's official mingw package is dynamic-only, so `SDL3.dll` ships alongside `mad2music.exe`); the handful of POSIX-isms (Winsock vs. BSD sockets, `_popen`/`localtime_s` vs. `popen`/`localtime_r`, `_getpid` vs. `getpid`) are isolated in `src/platform_compat.h` rather than scattered `#ifdef`s. On Windows `main()` also creates and holds a named mutex (`Mad2Music_SingleInstanceMutex`) for its whole process lifetime, both enforcing single-instance and letting `mad2podcastmod`'s native-Windows startup step (see its own bullet above, in "The chaos-effects system") tell whether an instance is already running before deciding to launch one.
- **`extern/sm64ex-alo`** — a vendored third-party Super Mario 64 PC port, the engine behind the `SM64Challenge` chaos effect (see `mad2companionmod` above). Built two ways from the same source, both via its own `Makefile` (not CMake): natively for Linux (`just build-sm64-linux`, preferring the `mad2-debian` distrobox if present) and best-effort cross-compiled for Windows (`just build-sm64-windows`, i686-w64-mingw32, `RENDER_API=D3D11` since no mingw `glew32` is readily available) for `mad2companionmod`'s real-Windows branch. Both need a user-supplied `baserom.us.z64` ROM dump (not part of this repo) to extract assets from. Talks to `mad2companionmod`/`mad2relauncher` over loopback UDP via a custom controller backend, `src/pc/controller/controller_udp.c`, added on top of upstream — see `mad2companionmod/include/mad2sm64_protocol.h` for the wire format shared by all three.
- **`extern/jak-project`** — a vendored fork of the OpenGOAL `jak-project` (Jak & Daxter decompilation/PC-port runtime, `github.com/open-goal/jak-project`), the engine behind the `JakChallenge` chaos effect (see `mad2companionmod` above). Native-Linux only (`just build-jak1-linux`, own `task`-based build, needs a user-supplied `jak1.iso` to extract assets from — no Windows branch, unlike SM64: `JakChallenge` is Wine-only). Produces `build/game/gk` (the runtime `mad2relauncher/jak1.go` forks) and `build/goalc/goalc` (the GOAL compiler — run `./build/goalc/goalc -c "(mi)" -g jak1` from this directory after editing anything under `goal_src/jak1/` to recompile). Unlike `sm64ex-alo`, `gk` has no socket primitive to receive controller input directly, so the last inch of the wire (`mad2relauncher` → a polled file, `mad2_input.dat`, inside this directory) is bridged by a hand-written patch in `goal_src/jak1/engine/ps2/pad.gc`'s `service-cpads` — see `mad2companionmod/include/mad2jak1_protocol.h`'s file header for the full picture, and this directory's own `saves_chaos/` (an isolated `--config-path`, separate from any real dev save data, that `jak1.go` always points `gk` at).
- **`extern/mario-legacy`** — a vendored *separate* jak-project fork, `OpenGOAL-Mods/Super-Mario-Legacy` (release v0.0.28, prebuilt `gk`/`goalc`/`extractor` for Linux **and** `gk.exe`/`goalc.exe`/`extractor.exe` for Windows, vendored side by side from that same release's two platform assets, sharing one `data/` tree — confirmed byte-identical file count and checksums between the two archives, so only the three Windows binaries needed adding, not a second copy of `data/`; no C++ build step either way, `just setup-mario-legacy` only extracts game assets and recompiles `goal_src/`), the engine behind the `MarioLegacyChallenge` chaos effect (see `mad2companionmod` above). Wine branch talks to `mad2relauncher/mariolegacy.go` exactly as before; the native-Windows branch (`mariolegacymod.cpp`'s `LaunchWindowsMarioLegacy`) launches `gk.exe` directly via `CreateProcess` and writes the same polled input file itself (no relauncher involved on that platform). Its release layout nests `goal_src`/assets under a `data/` subdirectory (unlike `extern/jak-project`'s top-level layout), so the injection file lives at `<this dir>/data/mad2_input.dat` on both platforms, not the repo root. Its `goal_src/jak1/engine/ps2/pad.gc` was confirmed byte-identical to `extern/jak-project`'s own aside from the same hand-written controller-injection patch, ported separately since the two forks share no source tree — see `mad2companionmod/include/mad2mariolegacy_protocol.h`'s file header. `libsm64` (statically linked into `gk`) auto-detects a Super Mario 64 `.z64` ROM next to the `gk` binary; `just setup-mario-legacy` symlinks in the same ROM `extern/sm64ex-alo/baserom.us.z64` already uses so the user only supplies it once. This fork does **not** carry `extern/jak-project`'s title-screen-skip/`*kernel-boot-level*` patch (confirmed absent upstream) — `-level`/`-boot -fakeiso` currently has no effect on either platform, a known gap, see `mad2companionmod`'s own bullet above.

**`mad2launcher`** is a separate, standalone Go+Fyne GUI (own `go.mod`, plain `go build`, no MinGW) — a desktop app for driving this repo without the CLI: auto-discovers `mad2`/`mad2russia`/`mad2demo` installs one directory level down from cwd (plus any `ExtraRoots` persisted in `mad2launcher_settings.json`), edits the selected install's `config.cfg` (every `[Section]` becomes a category in its dropdown — the same file `mad2config.dll` owns and every other mod reads from), launches the game with a level picker (`alchemy.go`'s `LevelNames`, ported from `../mad2mod/mad2rando.go`), and includes a save-file cheat-toggle editor (`saveeditor.go`, format ported from `../mad2assetextractor`'s save tooling — a fixed 13568-byte struct, PC little-endian or Wii big-endian, CRC32-terminated; only cheat toggles are exposed, not full save editing). It doesn't participate in the mod-loading chain at all — it's a UI convenience layered on top of the same install directories and config format everything else here uses.

### Deploy layout

`cmake --build build --target deploy-mad2` (or `deploy-mad2russia`/`deploy-mad2demo`) copies build outputs into the live game directory:
- `mad2modloader` → `<gamedir>/version.dll`
- Every other target → `<gamedir>/mods/<name>.dll`, **except** `mad2graphicseffectmod`, which deploys as `<gamedir>/mods/zz_mad2graphicseffectmod.dll` (see "D3D9 overlay hooking" above for why the prefix matters).
- `mad2gameeffectsmod/data/coordinates.yaml` (its `PlayerTeleport` coordinate pool) is additionally copied to `<gamedir>/coordinates.yaml` — the one non-DLL deploy artifact.
- `mad2nesmod`'s libretro cores + ROMs are *not* CMake deploy artifacts at all (they're fetched/user-supplied, not built) — `justfile`'s `deploy-mad2`/`deploy-mad2russia`/`deploy-mad2demo` recipes each additionally call a `_deploy-nes` step (after the `cmake --build ... --target deploy-*` above) that copies `extern/.libretro-cores/fceumm_libretro.dll`, `roms/smb1.nes`, `roms/smb2j.fds`, and `roms/disksys.rom` into `<gamedir>/nescore/`, and a sibling `_deploy-n64` step that copies `extern/.libretro-cores/mupen64plus_next_libretro.dll` and `roms/sm64.z64` into `<gamedir>/n64core/`, warning (not failing) per-file if any of them isn't present yet.

`GAME_DIR` (default `${CMAKE_SOURCE_DIR}/mad2`) is a CMake cache variable, overridable via `-DGAME_DIR=...`; the `mad2russia`/`mad2demo` deploy targets are separate, fixed-path targets defined alongside it in the root `CMakeLists.txt`'s `add_deploy_target()` calls.

### Logging conventions

Nearly every mod writes into **one shared, merged log file**, `<exe dir>/logs/mad2.log`, via a header-only cross-DLL helper (`mad2sharedlog/mad2sharedlog.h`, `Mad2Log_Write`/`Mad2Log`) rather than each owning a separate file — this superseded an older per-mod-file scheme. Every line still carries the writing mod's own bracketed tag (`[mad2xinput]`, `[SHADOWPASS]`, etc.), kept at each mod's existing `Log(fmt, ...)` call site, so the merged file stays attributable. Cross-DLL serialization is a **named Win32 mutex** (`Local\Mad2ModLoaderSharedLogMutex`), deliberately not a `CRITICAL_SECTION`: these are ~26 independent DLLs loaded into the same process, but DLLs do not share static/global state with each other — each gets its own copy of every global, including a `CRITICAL_SECTION` — so only a kernel object looked up by name actually serializes writes across DLL boundaries (this was a real, pre-existing gap in the old per-mod-file era: most of those loggers raced on a check-then-act lazy `fopen` with no cross-call protection at all). The file is opened, appended, and closed on every single call rather than kept open persistently, since persistent per-DLL `FILE*` handles to the same underlying file would each buffer/seek independently and can't be made safe just by adding a mutex around the write. It's header-only/inlined rather than resolved via `GetProcAddress` like the shared-API mods below: a named mutex + a fixed file path need no `DllMain`-time setup in some other "provider" DLL that might not have loaded yet — this matters concretely because the modloader itself must be able to log before any `mad2/mods/*.dll` has loaded at all.

Confirmed by grepping every mod's `src/` for `mad2sharedlog.h`/`Mad2Log_Write` usage rather than assumed: **every deployed DLL uses the shared logger except `mad2companionmod`**, which still logs to its own separate file, `mad2companionmod.log`, opened directly in the exe dir (not under `logs/`) — one `FILE*` guarded by a `std::mutex` in `sm64mod.cpp`'s `LogV`, which `jak1mod.cpp`'s and `mariolegacymod.cpp`'s own `Log()` wrappers forward to rather than opening independent handles (one log file per *DLL*, not per source file, since all three `.cpp`s link into a single `mad2companionmod.dll` — `jak1mod.cpp`'s own comment notes that two unsynchronized `FILE*` handles onto the same filename, one truncating and one appending, used to be a real interleaving/truncation hazard here before that consolidation). Migrating this last holdout onto `mad2sharedlog.h` is a mechanical follow-up, not done yet. When adding diagnostics, follow the existing tag convention (`[LevelLoad]`, `[SHADOWPASS]`, `[Override]`, `[Dependency]`, `[Diag]`) rather than inventing a new scheme.

### Asset format reverse engineering (`mad2iga`/`mad2repack`, `docs/`)

A separate, ongoing effort from the mod-loader DLLs above: reverse-engineering the game's actual asset formats (the Vicarious Visions "Alchemy" engine's IGA archive container and IGZ serialized-object-graph format) well enough to edit arbitrary game data, not just hook the running process. Lives primarily in `mad2iga` (the shared library) and `mad2repack` (the CLI exercising it), fully written up in **`docs/`** — read `docs/README.md` first, it's the index and gives an honest "what's solid vs. heuristic vs. open" summary; do not duplicate that content here, it changes often as the investigation progresses.

Two external reference sources have been essential and are worth knowing about if you continue this work: an unstripped Wii "Demo Action Pack" build's `Mad2.elf` (PowerPC, full symbol table — see `../mad2assetextractor/wii_demo_ref/`) provides a huge head start on per-class field layouts, but its offsets are **not** assumed correct on the PC build without independent verification (`docs/CLASS_SCHEMA.md`'s "Major caveat" — this was learned the hard way, more than once). The PC-side per-class `*InfoLib.dll` files (in `mad2/`, e.g. `ActorInfoLib.dll`, `ScriptInfoLib.dll`) are the actual source of truth and where every claim ultimately needs to be checked. A live Ghidra instance driven via the `ghidra-mcp` MCP bridge is the normal way to do this interactively; note that Ghidra's auto-analysis does not create `Function` objects at every export address in these DLLs/ELF — call `create_function` at the address of interest first (it picks up the already-demangled export name automatically), then `decompile_function`.

Current rough state (see `docs/README.md` for the up-to-date version): IGA archive container fully solved (verified round-trip); IGZ container header/sections solid, including a real object-graph walker (`mad2repack objects-dump`) that finds structurally-real objects; `.snds` audio fully solved and verified against the whole shipped corpus; `.texs` textures container-and-schema solved, pixel layout still open; `.hkt` Havok animation identified but not parseable yet. **Class field schema is now solved engine-wide**: `mad2metadumper` (see above) reads the Alchemy engine's own live class registry directly out of the running game process, yielding a complete, PC-verified, real-inheritance field schema for all 1392 registered classes (20,237 fields) in one capture — including the entire `TFBScriptInfo` namespace (cutscene/AI/trigger logic, the actual encoding of level *behavior*), which previously only had a semantic map with no offsets. `mad2repack script-dump` pulls full compiled scripts straight out of a real level with every opcode's own and inherited fields resolved. Instance *naming* (recovering a human-readable name for a given object, e.g. which `ActorInfo` is "which coin") remains the one unsolved, well-documented problem — see `docs/CLASS_SCHEMA.md`'s "Naming investigation" section before attempting it again, several approaches have already been tried and ruled out with concrete evidence (though a new, not-yet-followed-up lead surfaced this session: live-runtime-spawned UI objects' `igNamedObject` name field resolves to real readable names where the same field on static file objects doesn't, suggesting the name may only bind to a real pointer at runtime).
